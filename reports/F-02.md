## Implementation notes / deviations (small, all within the task's wording)
1. **Key order of the committed JSON** follows the zod schema order (e.g. person: … `past`, `after`, `quote`, `altQuote`, `guideLevels`, `guideNote`, `photo`, `consent`, `sources`), not the key order of the two oracle JSON files (which put `after` / `accessNotes` last and `sourceFile` mid-object for the station). The oracle test uses `toEqual`, which is order-independent, so it passes either way; byte-stability only requires a *fixed* order. If the orchestrator prefers the oracle files' literal order, it is a one-line change to `KEY_ORDER`.
2. **Strictness beyond the README (fail-closed):** `splitSections` throws on a `## ` line that does not match `## <label> · <fieldKey>`; `to-json.ts` throws on an unknown **front-matter** key as well as an unknown section key; `build-content.ts` throws on a duplicate person/station `id`. Blank lines inside bullet sections are skipped (not an error); all other non-`- ` lines throw.
3. `--check` also reports a stale `src/content/data/people/*.json` whose source file no longer exists, and `content:build` deletes such stale files, so build and check always agree.
4. Nested objects (`quote`, `guideLevels`, `photo`, `consent`, `location`, `silenceMoment`, `sources[]`) are also written in a fixed key order; `location` / `silenceMoment` are rebuilt from the YAML mapping (unknown nested keys are dropped before zod's `.strict()` would see them — zod still validates all required nested fields).
5. Diagnostics go to `stderr` (`no-console` is a lint warning and lint must be warning-free).
